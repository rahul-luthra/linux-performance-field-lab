The Canary Failed: Rolling Linux Patching with AWX

Two Ubuntu VMs served quotes behind one load balancer. I tested a successful rollout and a failed canary to see whether traffic stayed healthy while AWX applied an update, rebooted the hosts, and checked the application.

What the two runs showed

AWX upgraded tzdata from 2024a-2ubuntu1 to 2026e-0ubuntu0.24.04.1. I scheduled a reboot on each patched host to exercise the rolling maintenance path.

Client errors count requests that were actually sent. The probe skipped some scheduled sends, with a longest gap of 47.87 seconds between sent requests.

In the failure trial I injected an application regression on the canary after its reboot. The endpoint returned HTTP 200 with the wrong quote. The body check failed, AWX left the canary out of rotation, and the peer patch job did not launch.

    AWX marked the failed-canary workflow successful because its containment branch completed. The canary node shows the failed check, and the peer node shows that it was skipped.

    How I ran the change

    AWX checked disk space, the package candidate, and a real quote on both hosts before approval. It drained one VM, waited for requests already in flight, applied the update and rebooted. A host could rejoin only after the package, boot, and quote checks passed.

    For recovery I restored the failed canary’s powered-off VirtualBox snapshot while the peer carried traffic. I verified the previous package version, a new boot identity, and the correct quote before putting it back into rotation.

    The client scheduled four requests per second. The two trials exercised one Ubuntu package and a controlled application regression. The availability figures apply to the measured traffic and lab conditions.
