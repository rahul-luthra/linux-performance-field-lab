How to reason from the evidence
Delay: compare HTTP connect/response timing with TCP RTT and the server's handler timing. Retransmissions also occurred in baseline and delay-only runs, so they do not by themselves prove configured packet loss. Loss: examine queue drops and sender retransmissions; look for occasional long waits rather than assuming every request slows equally. Bandwidth: compare bulk-transfer and iperf results with small-message latency. Application pause: compare handler elapsed time with socket RTT and handler CPU time.
The injected conditions identify controlled causes. Removal and recovery test reversibility. Random loss is stochastic, tail percentiles come from a short sample and both VMs share one physical host. Client CPU averaged roughly 54–79% in early HTTP windows and about 6% in the corrected tail. This background variation limits exact attribution of HTTP tail differences. Scheduler activity, caches and interface offloads can affect results; these are diagnostic experiments, not a production link-capacity certification.


Scope and reproducibility
Oracle Linux 9.7 · iperf3 3.9 · Python standard library · bounded in-memory payloads · one-second host/TCP observations · short text-only packet-header captures. The load generator shares the client VM, so scheduling lag and both hosts' CPU use are retained.
Privileged setup controls the firewall, transient services and network queue; the application and throughput service run as the ordinary lab user. Temporary access rules expire automatically and are removed after the run. The original queue policy is restored. SELinux remains enforcing. The existing NFS mount is retained with its updated address.
