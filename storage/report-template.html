What changed across the experiments?

Read the result without overclaiming

The 20 ms intervention delays only server-to-client TCP packets from NFS port 2049. Its repeated rise in WRITE round-trip time, followed by recovery after removal, supports the injected network-path explanation. It does not prove a natural network fault.

The background IOPS cap reduced competing work, but did not establish a reliable latency fix: HTTP p95 changed from 30.7 to 61.7 ms in the first pair, then 246.4 to 199.2 ms in the repeat. The final quiet run still measured 235.4 ms. This late baseline drift remains unresolved; virtual/backing storage, filesystem work and host scheduling need further evidence. A lower disk-busy chart alone does not prove improvement.

The local/NFS baselines are observations on two VMs sharing one physical host, with separate virtual disk images and caches. They are not independent physical disks or a universal local-versus-NFS speed ranking. The workload is small, sequentially acknowledged, and deliberately below a production capacity test.

Setup and scope

NFSv4.2 over hard/TCP mounts · synchronous export · root squashing · numeric UID/GID matched · export and firewall restricted to the single lab client · nodev/nosuid/noexec client mount.

The cloned server received a new machine ID and SSH host keys, and boots without the desktop. SELinux enforcement was retained. sec=sys trusts the allowed client's identities; this is a trusted-LAN teaching setup, not encrypted or Kerberos-authenticated production storage.

Each app file is capped at 16 MiB; competing writes use a separate preinitialized 64-MiB file and bounded runtimes. Checksums and readback test the observed data path. Java's remote-file force contract and the virtualized storage stack do not provide a tested physical power-loss guarantee.
