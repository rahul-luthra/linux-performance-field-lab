Interpretation boundaries

A JVM heap error is not proof of a leak. The retained-set tests request finite, known amounts of memory. Increasing the heap fixes that sizing mismatch in the observed window; it would not fix unbounded retention.

A SIGKILL alone is not proof of OOM. This lab requires an increment in the same cgroup's OOM-kill counter as well as Java's signal exit to classify a Linux memory-limit kill.

Reusing buffers changes allocation and memory-locality costs. Latency differences cannot all be assigned to garbage collection. GC counters, CPU time and repeated runs provide context; there is no randomized or production-scale benchmark here.

Fresh-array run A retained elevated recovery latency despite no GC-counter increase in that window; the repeat recovered. Its cause remains unresolved. The report preserves that discrepancy rather than attributing it to GC.

All units run one at a time, with at most 192 MiB service memory and swap disabled for the test cgroup. The supervisor preserves post-exit counters. Host PSI was unavailable. Binary heap dumps stay outside the public package.
