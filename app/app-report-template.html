What the evidence can tell us

Compare handler wall time with thread CPU time. A larger wall-time increase than CPU-time increase supports investigating time spent waiting to run. Runnable queues, per-process counters and a Java execution profile provide supporting context.

Recovery here follows the end of an injected workload. The 150 ms latency threshold in the raw analysis is illustrative; it is not a production service objective.

Java execution profile

Flight Recorder sampling covers warmup and both experiments. Samples identify executing code; they do not measure scheduler wait time. Full JVM recordings are kept separately from the public package.

Scope and reproducibility

Oracle Linux 9.7 · 2 logical CPUs · about 1.5 GiB RAM · OpenJDK 17 · Java heap capped at 64 MiB · service memory capped at 256 MiB · loopback only.

The client and app share the VM, so client scheduling is a possible confound. Scheduling lag is recorded separately, and handler timings offer a server-side cross-check. Background workload, JVM warmup, sampling and profiling also affect measurements. This experiment exercises CPU contention; it does not test storage, memory exhaustion or production network behavior.
